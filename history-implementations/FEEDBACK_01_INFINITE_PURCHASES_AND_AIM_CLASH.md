# FEEDBACK-01 — Infinite purchase usability and faster, larger Aim Clash on phone

## Owner feedback — 27 October 2026

The first physical-phone playtest of the integrated private game was broadly positive ("the base is solid"), but raised two concrete issues:

- **Infinite World:** "I can't buy anything." Do **not** assume the owner means the initial cash balance, a server/DataStore failure, inability to locate the shop, an unresponsive Buy button, or a purchase that succeeded but stayed in storage. Investigate each possibility and make the flow understandable and functional.
- **Aim Clash:** it feels too slow and the arena should occupy more of the phone screen. Preserve the existing direct tap/click premise, server-validated 1v1, scoring model and overall feel; this is tuning and mobile UI, not a redesign.

Proceed with meaningful fixes without asking the owner to reproduce every hypothesis. If the live failure cannot be reproduced, distinguish verified code/UX defects from still-unconfirmed live-service causes. Keep it simple and reversible.

## Actual current code / hypotheses to verify (reinspect latest main)

At briefing, latest main is `f5f7febaee498c5923797aedf1a2203a19793704` (integrated PR #35 and publisher fix #36), deployed to the separate private four-place development experience. Start from current main and read `AGENTS.md`, `docs/INTEGRATE_01_REVIEW.md`, `docs/MOBILE_DEPLOYMENT.md` and these modules:

- `src/client/PropertyEditor.luau`: `My place → Discover → item → Buy for X cash`; purchase requests use `TycoonProperty` RemoteFunction. After a purchase the UI re-renders the catalogue. The initial buy does **not** visibly place the object.
- `src/server/PropertyEdits.luau`: new items are purchased into an object with `stored = true` (unless a fixed expansion). Therefore a purchase can succeed without anything appearing in-world; it must be placed from Arrange. The server returns rejection messages such as "Need X more cash" and "First discover …". The client must surface them.
- `src/server/TycoonRuntime.luau` and `src/server/Persistence/Profiles.luau`: the server rate-limits property requests with `Config.RequestInterval = 0.25` seconds; a quick request can return `{available=false,message="Please wait a moment"}`. In `PropertyEditor.request`, *every* nonavailable reply drops `snapshot` and re-renders only "Refresh my place", which may unnecessarily eject a valid, ready user from the catalogue. Treat this as a suspected reproducible UI defect; test it explicitly. Do not relax server-side flood protection or retry an ambiguous buy automatically.
- `src/shared/Config.luau` and `src/server/Persistence/ProfileSchema.luau`: a genuinely new Infinite profile starts at **0 cash** and accrues **1 cash/second** while Ready; cheapest visible first discoveries (Seed nursery, Potter's wheel and Prism table) each cost **12 cash**. This initial wait may be unclear to a new player, but do not silently change prices, grant currency, or alter progression without evidence that balancing is needed.
- `src/shared/Experiments/AimClash/Rules.luau`: 24 targets with interval stages **1.0 / 0.7 / 0.46 seconds** (roughly **17.2 seconds** total).
- `src/client/Experiments/AimClash/View.luau`: `Rules.boardSize` reserves substantial vertical space for five toolbar buttons, status and footer. On the previously tested ~800×354 safe-area phone-landscape layout the board can shrink to approximately **190 pixels** across; this supports the owner's "too small" report. Keep `GuiService:GetInsetArea` coordinate/safe-area correctness and ensure pointer coordinates still align to visuals.

## Work A — make Infinite's first purchase discoverable and reliably actionable

1. On a **Ready** profile with at least 12 cash, verify a real client can open My place, choose the first accessible discovery, tap Buy, receive an authoritative result, and find the newly owned item. Test both mouse and native emulated touch, plus direct phone-inspired rapid tap timing. Start from a *fresh* profile and from a returning one. Keep real live DataStore/phone outcomes unverified until observed.
2. Fix the proven request-throttle/client-state interaction: a temporary "Please wait" must not erase a valid catalogue or force a repeated Refresh loop. Preserve the trusted server's rate limit, profile lease/epoch, revision/sequence fencing and duplicate purchase protection. Represent busy/temporary/rejected/unavailable separately on the client. Never show "success" before server confirmation, never auto-repeat a buy with unknown completion, never overwrite saved data or invent a new profile after a load failure.
3. Show exactly why Buy isn't currently possible: funds, missing prerequisite, owned limit, loading/unavailable, stale state, network ambiguity. Make the cash balance and readiness visible in the purchase context; if affordable, make Buy visually actionable; if not, show how much is missing and allow the player to see the balance rise. No dead/unresponsive button or silent return to main list.
4. On confirmed purchase, give obvious success feedback, clearly say **"Purchased — in storage"**, and provide a direct **"Place now"** route to arranging that newly bought object. Keep the existing validated placement preview/confirm path and ability to store items. For a fixed unlock like rear garden, explain that no placement is needed. Do not auto-place in an invalid position or consume another purchase. Preserve previously owned objects and movement/palette functionality. Don't unilaterally convert Infinite to Factory's walk-over pads; it is a distinct persistent creative mode.
5. Remove outdated Infinite Help text that mentions only a four-upgrade catalogue, and include a one-line first-time instruction in the HUD or shop: "Earn 12 cash → My place → Discover → Buy → Arrange". Avoid intrusive tutorial overlays and visual clutter. Keep touch targets scrollable and readable in landscape/portrait.

## Work B — Aim Clash faster and larger on a phone

1. Try an initial **faster default** of **0.70 / 0.50 / 0.35 seconds** per target in the first/middle/final eight, about 12.4 seconds for 24 targets. Treat these as a starting tuning target and keep the three sections configurable; adjust if real interactive tests indicate unreadable target timing on an ordinary phone. Preserve the same server-controlled pattern/seed/timing for both duel players, same target opportunities, hidden intermediate scores, server judgement and independently calculated Precision. Recompute all fixtures and expected durations from authoritative rules, not hardcoded stale results.
2. Give the active arena much more of the **safe landscape viewport**, without obscuring the circles, next-location hints or trail. Prefer collapsing/hiding disabled lobby controls *during countdown and active play*, compacting status/footer, or reorganizing the toolbar rather than only increasing `TargetRadius` or rendering offscreen. The arena should be measurably larger than its current approximately 190px landscape baseline on an ~800×354 safe viewport, ideally around 240px or more when feasible. Preserve accessible Modes/return and any necessary motion settings; don't make the menu invisible or unclickable. Keep a stable arena size through a round once its countdown begins.
3. Preserve and test portrait, landscape, notches/top-bar, gamepad menu navigation (no false claim that gamepad aiming exists), physical touch-sized targets, mouse input, UI hit tests and accurate `InputObject.Position` versus `GuiObject.AbsolutePosition` coordinate alignment. Avoid accidental hit reports when interacting with controls or panels.
4. Distinguish **designed target cadence** from actual **frame rate / input lag**. Collect bounded instrumentation on the same mobile-emulated setup if possible. The existing INTEGRATE-01 evidence showed severe Studio frame spikes; do not claim a performance pass from a shorter target schedule. If it causes missed targets during stalls, adjust responsibly and report the trade-off rather than weakening server scoring/anti-spam checks.
