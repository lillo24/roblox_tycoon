# DEPLOY-01 — One-click GitHub → Private Roblox Mobile Playtesting

## Outcome

Implement the simplest reliable **manual, one-click development deployment** for `lillo24/roblox_tycoon`. The owner should be able to merge game changes to `main`, open GitHub's **Actions → Deploy Development → Run workflow** from a PC or phone, and rejoin the private development experience in the Roblox mobile app to play the new version wirelessly. No USB, APK, always-on PC, or repeated Studio publishing should be required **after the first-time Roblox/GitHub account setup**.

This is an **implementation prompt**, not authorization to publish anything now. The first use of the workflow must be an explicit manual dispatch after the owner finishes credential and target setup. Never silently convert this into automatic on-push deployment or a public release.

## Repo-specific starting point (reinspect before coding)

Read `AGENTS.md`, the current `README.md`, `place/README.md`, `scripts/README.md`, `default.project.json`, `.github/workflows/validate.yml`, and the actual source/build helpers before changing files. Work from **latest `main`** in an isolated branch/worktree; follow PR, CI, documentation, merge, and cleanup rules from `AGENTS.md`.

At prompt creation, `main` contains a real Studio-authored six-lot FactoryHub scene at `place/tycoon.rbxlx` plus Rojo-owned current source under `src/server`, `src/shared`, and `src/client`. A bare `rojo build default.project.json` is **code-only** and would not publish that map. The existing `scripts/New-UiReviewPlace.ps1 -GameplayOnly` combines the saved scene with current mapped source, excludes QA fixtures, and validates that the canonical scene is unchanged. Investigate reusing/refactoring that proven mechanism instead of building a second unrelated assembler; preserve the current QA-preview contract.

The existing `.github/workflows/validate.yml` tests PRs and manual runs, not releases. Existing experimental/Infinite/mode/performance PR branches are **not automatically part of `main`**. Do not merge them or publish one of their scratch previews to make deployment appear to work. Keep this infrastructure change independent. The proposed MODE-01 routing may eventually require multiple places: implement **one existing start place** now; document future multi-place expansion rather than guessing destination IDs.

## Implement autonomously — even before account setup is available

1. Add a **`workflow_dispatch`-only** GitHub Actions workflow, visibly named **Deploy Development**, in `.github/workflows/`. It must operate only on the latest default branch `main`, reject a non-`main` dispatch/ref, and never run automatically for a push, merge, pull request, schedule, or tag. Use a job concurrency group that prevents overlapping deployments to the same development place. Give GITHUB_TOKEN minimum `contents: read` permissions. Pin maintained action versions consistently with repository policy. Use `windows-latest` / PowerShell and the already pinned Rokit/Rojo toolchain unless a documented, demonstrated improvement justifies otherwise. Don't introduce a platform-wide dependency or external deployment service.

2. Keep target configuration out of source: use **GitHub Actions variables** `ROBLOX_DEV_UNIVERSE_ID` and `ROBLOX_DEV_PLACE_ID`, and **GitHub Actions secret** `ROBLOX_OPEN_CLOUD_API_KEY`. If an environment named `roblox-development` helps protect credentials and limit the target, use it and document any required manual GitHub environment settings. Check variables are valid positive decimal IDs and the secret is supplied, fail **before a network publish** if any are absent, and never print the secret or echo authorization headers. A secret must never be stored in committed source, a build, a log, or a downloadable artifact. Never hardcode guessed IDs or publish to a generic fallback. A failed preflight must produce an actionable message.

3. Run the appropriate **full repository validation** on the actual commit to be deployed, not merely a green status from an unrelated PR. Preserve the current PR validation workflow/behavior. Construct a **fresh gameplay-only publishable `.rbxlx`** from the canonical `place/tycoon.rbxlx` plus exact current `src/` scripts. Do not publish `build/validation.rbxlx`, the canonical snapshot without verifying code freshness, an older preview, test/QA fixtures, or synthetic display data. Build inside ignored `build/`, leave tracked scene/source untouched, and verify the assembled file's Workspace matches the canonical scene, all managed source/class paths equal this checkout, and QA-only folders/remotes/scripts are absent. It is acceptable to introduce a dedicated deployment wrapper around the existing preview builder. Reject missing or unsafe build inputs rather than silently uploading an incomplete map.

4. Implement a small testable publisher/wrapper that uses **Roblox Open Cloud Place Publishing**, with the target IDs from Actions variables, a fresh `.rbxlx` with `Content-Type: application/xml`, the `x-api-key` secret in a request header, and the currently documented published-version endpoint:
   `POST https://apis.roblox.com/universes/v1/{universeId}/places/{placeId}/versions?versionType=Published`.
   Verify the live official API contract when coding. Correctly handle non-2xx responses, timeouts, invalid response JSON, and missing/nonpositive `versionNumber`; do not declare success when only an upload command exited. Avoid leaking the credential through verbose HTTP output or exception serialization. Do not retry an ambiguous successful upload automatically: repeated uploads can create additional versions. Keep a concise, redacted, actionable failure report. Record target place/universe IDs, commit SHA, deployment build digest, and returned published version in the GitHub job summary. When practical, retain a short-lived gameplay-only build artifact for audit, never a secret-bearing file.

5. Add meaningful **offline regression tests** that prove a missing secret/ID cannot publish, the wrong branch/ref is refused, validation/build must pass before HTTP is attempted, QA/fixtures cannot enter the deploy build, correct content type/payload/endpoint are used, and mocked HTTP failures/invalid replies remain failures. No Roblox credentials should be required for CI or local dry runs. Prefer a dependency-injection/mock transport seam over hitting Roblox during ordinary validation. Update repo validation/CI checks as needed so changes are actually tested, and keep expensive work scoped appropriately.

6. Document the operator workflow in a concise `docs/MOBILE_DEPLOYMENT.md`, link it from the root `README.md`, and update `scripts/README.md` or the nearest file for changed commands/configuration. Cover one-time first publish/create of a **separate private development Roblox experience** (not the eventual public game), how to create it from a fresh gameplay-only scene rather than stale saved script copies, where to find Universe ID and Place ID, how to create a **single-experience, universe-places Write-only API key**, where to add the GitHub secret/variables, GitHub Actions manual run on `main`, how to check the published version, and how to rejoin the game in the Roblox **phone app**. Clearly explain that publishing a new version is **not** hot-reloading a currently running client/server: close and rejoin, and allow for existing servers that may still be running an older version.

7. Keep Roblox audience **Private** by default (owner and users with Edit permission); do not grant general access, switch to Public/Limited, turn on production DataStore access, create monetization, restart live servers, alter hosted production settings, or assume a friend can play a private experience with Playtest-only access. If later testers need access, document the separate owner decision for an eligible **Limited → Playtesters** audience or suitable edit permissions; do not make that audience change unilaterally. Test environment/Universe IDs must remain distinct from any production game. If future MODE-01/Infinite builds need additional places, cross-server TeleportService, or DataStore persistence, treat that as a separate audited expansion.

8. Account for the official Place Publishing API limitation: some instance types such as `EditableImage`, `EditableMesh`, `PartOperation`, `SurfaceAppearance`, and `BaseWrap` do not get updated correctly through this API when modified. Inspect the scene for these types, document whether the present build is affected, and fail/warn clearly if a change requires manual Studio publishing; do not silently imply perfect fidelity for unsupported asset types.

## Work policy and finishing conditions

Proceed through **all repo/code/build/test/documentation work without waiting** for the user's key, IDs, Studio login, phone, or manual approval for ordinary implementation choices. If credentials/experience do not yet exist, finish and verify a complete **dry-run-capable** workflow with mocked publishing and clear missing-configuration behavior. Do not use your own Roblox account, copy local browser/session cookies, scrape login, ask the user to paste a key into chat, or forge a live success.

Follow `AGENTS.md`: isolate implementation in a branch/worktree, validate, inspect diff, commit/push, open a PR, and merge only after required checks pass and no consequential manual-review hold remains. A source PR merge **does not authorize invoking the deployment workflow** or publishing a Roblox place. Leave any external setup/publishing as explicit owner actions. Do not merge unrelated game-feature branches.

In the final handoff, distinguish precisely between implemented + tested offline, PR/merge status, and live first-deployment/physical-phone QA **not yet executed**. Provide clickable paths to the GitHub Actions workflow and setup document, the exact names of the three required secret/variable entries, and the smallest remaining owner actions. If all prerequisites later become available, the owner should need only **Run workflow** and **open/rejoin in Roblox** for repeated updates.
